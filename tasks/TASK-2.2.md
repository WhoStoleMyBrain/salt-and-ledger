Finish the user-facing harbor workflow and shared private local stock *end to end*, including atomic economic ownership and save compatibility. **Do NOT implement:** multi-stop automatic itineraries (next task), captains, character/charter draft, blessings/curses, economic rebalancing, fees/taxes, bank loans, more goods/towns, speculative quest frameworks, or a wholesale redesign of every legacy screen. Preserve v1/v2 and all old v3 runs/saves/tests, in particular the original golden experiment bytes. Don't spend the task on a site-wide styling overhaul unrelated to the core workflow.

### B. One practical harbor work surface

1. A selected owned ship + town should expose **town market**, **selected ship hold**, **company's local stock**, and clear buy/sell/load/unload actions together. A town without a ship should still allow the owning company's local market↔stock transactions and show its production. Show no false access to remote ship cargo.
2. Suggested navigation: select/right-click town with player ship selected → harbor/trade; select/right-click town without a player ship → town/company stock/industry if owned; also include discoverable visible buttons and keyboard access. Correctly handle selected NPC ships, docked versus remote selected player ships, modal close/back/focus, and paused automation. Never make right-click the only way in.
3. **Market purchase/sale is paid; ship↔company stock movement is a physical no-cash transfer.** At port show whole cargo constraints, exact marginal bid/ask, total and average executed price from authoritative previews, quantity presets (1 / 5 / max, ±), market affordability, input/outflow stock and blockers. Never reimplement pricing in UI. Preserve the existing zero-time trade/transfer and stale-revision protections.
4. Use compact scannable rows (commodity, market, ship, local stock, real bid/ask) and short clear status labels. Show stock relative to actual household/recipe needs, with neutral/adequate/shortage/surplus labels and accessible colors/icons. Make explicit whether a row's price is **buy** or **sell**, and whose cash pays. Full calculations live in expandable detail, not permanent paragraphs.
5. Simplify map HUD / 'Your Enterprise' into a few highly useful values (day, cash, Company Value, 0–4 objectives/remaining time, selected ship/port and important blockers). Remove duplicate Ascension explainer text and lengthy economic prose from the primary play surface; do not lose the information: move detailed rules into context help/encyclopedia. Preserve Compact/Default/Large/XL readability; don't shrink fonts to fit.
6. Better blocked actions: display the **specific immediate cause and an actionable remedy**: missing input, wrong port, storage full, employer wage funding, unaffordable stock, depleted market cash, disabled automation, construction, price threshold or missing capability. Use existing authoritative reason codes/preview outcomes; no misleading generic 'cannot trade'.

### C. Shared company stock per town — authoritative new rules

User expectation: Grain enters the **company's town warehouse**, an owned local Mill consumes it and deposits Flour, and an owned Bakery in the same town consumes that Flour and Logs, without manual facility-to-facility steps. Production is still made only by real facilities, paid wages, whole batches, with capacity, input and output limits. This is **not shared with the public market, NPC companies or other towns**.

1. Introduce a single explicitly owned `(companyId, portId)` **local company stockpile** for new runs. Multiple owned facilities at that port operate on this shared stock. An owned ship may transfer only at the actual dock; market↔stockpile trades use the ordinary local warehouse trade/quote/calculator. No goods teleportation. Keep exact fractional quantities and FIFO lots/basis once, not one projected copy per factory.
2. Define and document a deterministic **aggregate capacity** rule derived from actual constructed facilities/warehouses; no free infinite space. Also define sane per-recipe output blocking under pooled stock; multiple buildings of the same type must still have reason to exist. Pending and granted facilities, construction and default automation must follow these capacity and ownership contracts. Implement a no-double-count Company Value computation and exact material costing through production/transfers/sales.
3. Keep facility identity and per-facility production counters, payroll, construction state, and policy control distinct. **Separate industrial labor from shared material storage.** Clearly attribute consumed/produced lots and blocked reasons without falsely assigning all shared inventory to every facility. If needed expose a new town stockpile snapshot, and have old facility inventories remain only in old-rule worlds.
4. **Compatibility is critical.** Existing schema-1/2 saves and v1/v2/v3 worlds (including the supplied completed v3 save) must load and continue **with their old per-facility storage semantics**, without silent migration or altered signatures/bytes. Introduce an explicit independently versioned `CompanyStorageRules` (e.g. legacy v1 vs pooled v2) for **new scored v3 runs**. Old save identities default to v1 when the field is absent; new v3 starts use v2. Include version in new run identity/comparison group, full state fingerprints and new schema (e.g. schema 3), while old codecs retain original format for old identities. Do not change the geography/content generator seed and signatures merely to introduce storage. For a legacy saved run the UI should display the actual legacy facility stores, not invent a pooled account.
5. Apply the shared-stock model consistently in player private construction, production, exact accounting, procurement/sale policies, manual ship/storage transfers, old two-port industrial automation where applicable, charter grants, public snapshots, challenge progress and UI. Existing plain v3 route policies may require a compatibility adapter to the new shared stock: validate that a source/destination facility belongs to the correct company and port, then consume from the town's authoritative store exactly once. Existing NPC simulation remains legitimate and finite.
6. Do not quietly consolidate two warehouses by adding their capacities and removing their FIFO provenance in an old save. New-run start constructs pooled stores explicitly; no ad hoc migration is required for this milestone.

### D. Clear end-of-run state and developer exports

1. Economic victory must still **commit and freeze immediately**, but the Unity host should visibly acknowledge an achieved objective/Grand Commission before switching to results (e.g. dismissible completion panel with 'View results'). No duplicated success, accidental day advances or forced wait animation. Result and frozen save remain inspectable, including journal.
2. Add a **development/diagnostics-only 'Export Run Report'** option on save/results/ledger surfaces. Export an exact raw world-save JSON plus one human-readable Markdown or JSON diagnostic report: identity/seed/charter/draft, day/revision/status, objective progress and reasons, all company/town/household/NPC/treasury/outside accounts, stock and goods, ownership/FIFO totals, ships/routes, facilities/input/wage/output status, priced goods/targets and bounded recent events. Label bounded history as partial; don't claim a full historic ledger if not retained. Export under a discoverable `Application.persistentDataPath/Exports` folder, print/show precise file paths to user. Safe filenames, size limits, no overwrite without explicit intent.
3. Preserve the three existing local save slots and terminal save semantics. Export is read-only and must never mutate a world, change a draft or advance time.
