# Unity 6 integration and verification

The existing project at `unity/` uses **Unity 6000.6.6f1**. Its Bootstrap scene loads canonical content and runs the same production command as the .NET 10 console demo. Simulation source remains only in `src/SaltAndLedger.Simulation`; the host adds no economic rules.

## Prepare a checkout

Install the Editor version in `unity/ProjectSettings/ProjectVersion.txt`, the .NET 10 SDK, and the Python dependencies. From the repository root:

```powershell
python -m pip install -r requirements.txt
dotnet restore SaltAndLedger.sln --locked-mode
python tools/prepare_unity.py
python tools/prepare_unity.py --check
```

Preparation validates the canonical data and rebuilds the existing `netstandard2.1` library in Release using locked dependencies, even if a previous DLL exists. It stages:

| Generated asset | Source |
| --- | --- |
| `unity/Assets/Generated/Simulation/SaltAndLedger.Simulation.dll` | Release build of the existing simulation project |
| `unity/Assets/Generated/Resources/CanonicalContent.json` | Exact bytes of `data/content.json` |
| Asset/folder `.meta` files | Stable GUIDs generated by the preparation tool |
| `unity/.simulation-staging.json` | Source, build configuration, and output hashes |

These files are ignored build outputs. Rerun preparation after editing the simulation, canonical data, schema, or relevant build configuration. The read-only `--check` command detects changed inputs, missing/modified outputs, and unexpected files in the generated directory; it requires no SDK or `bin/` directory. It does not import or run Unity. Use `--dotnet PATH` if the .NET executable is not on PATH.

Open `unity/` through Unity Hub and allow package resolution/import to finish. Use the project's **.NET Standard 2.1** API compatibility level under Player settings. Unity documents this profile for [managed plug-in compatibility](https://docs.unity3d.com/6000.0/Documentation/Manual/dotnet-profile-support.html). The existing template assets and packages are retained; their presence does not add simulation functionality.

## Newtonsoft ownership

The portable build uses NuGet **Newtonsoft.Json 13.0.3**. Unity's manifest directly pins **`com.unity.nuget.newtonsoft-json` 3.2.2**, and its UPM lock file is committed. Unity supplies the only Newtonsoft assembly used by the Unity host. Do not copy the NuGet Newtonsoft DLL, the .NET 10 demo/test assemblies, or simulation source into `Assets`.

Unity's [package manual](https://docs.unity3d.com/Packages/com.unity.nuget.newtonsoft-json@3.2/manual/index.html) identifies upstream version 13.0.2. Inspection of the installed 3.2.2 package confirmed file version 13.0.2 and assembly identity `Newtonsoft.Json, Version=13.0.0.0, Culture=neutral, PublicKeyToken=30ad4fe6b2a6aeed`, matching the NuGet 13.0.3 assembly identity. This resolves the assembly reference; behavioral compatibility is established only for the configurations exercised below. The package version and upstream library version are different numbering schemes.

## Editor smoke and integration tests

Open **`Assets/Scenes/Bootstrap.unity`** and enter Play mode. The **Production Smoke Test** GameObject has `SaltAndLedger.UnityHost.ProductionSmokeTest`, whose `Start()` calls `RunSmokeTest()`. It loads `Resources.Load<TextAsset>("CanonicalContent")`, invokes `ContentLoader`, `Inventory`, and `Production.TryRunBatch`, and checks the outcomes. The Console must show:

```text
Initial: logs=6, planks=0
Batch 1: produced; logs=4, planks=1
Batch 2: produced; logs=2, planks=2
Batch 3: produced; logs=0, planks=3
Batch 4: insufficient inputs; logs=0, planks=3
Salt & Ledger smoke passed: logs=0, planks=3; rejected batch left inventory unchanged.
```

A missing staged asset or invalid outcome fails explicitly. No Inspector content assignment or source duplication is needed.

Open **Window > General > Test Runner** and run:

- **Edit Mode:** `SaltAndLedger.UnityHost.EditModeTests` (2 tests covering production and the single UPM Newtonsoft provider, including a hash comparison of the loaded DLL against the pinned package binary).
- **Play Mode:** `SaltAndLedger.UnityHost.PlayModeTests` (1 test that loads Bootstrap and checks the component's actual `Start()` result).

For repeatable command-line tests, close the Editor instance using this project first, or use a separate complete checkout prepared with the same commands. Do not launch a second Editor against an already-open project. The PowerShell examples below run from the repository root; change the Editor path for your installation. Piping to `Out-Host` makes PowerShell wait for the GUI executable to finish.

```powershell
$unityEditor = 'E:\UnityInstalls\6000.6.6f1\Editor\Unity.exe'
$unityProject = (Resolve-Path 'unity').Path
$resultsDir = Join-Path $PWD '.cache/unity-results'
New-Item -ItemType Directory -Force -Path $resultsDir | Out-Null

& $unityEditor -batchmode -nographics -projectPath $unityProject `
    -runTests -testPlatform EditMode -assemblyNames SaltAndLedger.UnityHost.EditModeTests `
    -testResults "$resultsDir/editmode.xml" -logFile "$resultsDir/editmode.log" | Out-Host
if ($LASTEXITCODE -ne 0) { throw "Unity Edit Mode failed: $LASTEXITCODE" }

& $unityEditor -batchmode -nographics -projectPath $unityProject `
    -runTests -testPlatform PlayMode -assemblyNames SaltAndLedger.UnityHost.PlayModeTests `
    -testResults "$resultsDir/playmode.xml" -logFile "$resultsDir/playmode.log" | Out-Host
if ($LASTEXITCODE -ne 0) { throw "Unity Play Mode failed: $LASTEXITCODE" }
```

Do **not** add `-quit` to `-runTests`: the test runner owns completion and Editor exit. Inspect the NUnit XML files for a passed result and the expected nonzero test count, as well as the Editor logs; an exit code alone is insufficient evidence. See Unity's [Test Framework command-line reference](https://docs.unity3d.com/6000.2/Documentation/Manual/test-framework/reference-command-line.html).

## Windows Mono player

With Windows build support installed, the following entry point builds only Bootstrap to `unity/Builds/Smoke/Windows/SaltAndLedger.Smoke.exe`. It temporarily chooses Mono and restores the previous backend setting. The first build can take several minutes compiling shaders from the retained template packages, including the inference package; allow this compilation to finish. Use the variables from the test commands above:

```powershell
& $unityEditor -batchmode -nographics -quit -projectPath $unityProject `
    -executeMethod SaltAndLedger.UnityHost.Editor.SmokePlayerBuild.BuildWindowsMono `
    -logFile "$resultsDir/build-mono.log" | Out-Host
if ($LASTEXITCODE -ne 0) { throw "Unity player build failed: $LASTEXITCODE" }

$smokePlayer = Join-Path $unityProject 'Builds/Smoke/Windows/SaltAndLedger.Smoke.exe'
& $smokePlayer -batchmode -nographics -saltAndLedgerSmokeTest `
    -logFile "$resultsDir/player-mono.log" | Out-Host
if ($LASTEXITCODE -ne 0) { throw "Unity player smoke failed: $LASTEXITCODE" }
Get-Content "$resultsDir/player-mono.log"
```

The `-saltAndLedgerSmokeTest` flag exits the player with code **0 only after all smoke assertions pass** and code **1 on failure**. Confirm the exact completion message in the player log. Normal Play mode and a player launched without this flag remain open. A blank scene with Console/log output is expected; graphical presentation is outside this task.

## Verification record and limits

Task 0.5 verification was run on Windows on 2026-10-17 with Unity 6000.6.6f1. Editor and player checks are separate from standalone checks; one result cannot substitute for another.

| Check | Result |
| --- | --- |
| .NET 10.0.402 SDK / 10.0.13 runtime, Release solution build | Passed, zero warnings/errors |
| Standalone .NET 10 regression tests | 90 passed |
| Console demonstration | Three successful batches; rejected fourth batch leaves 0 logs / 3 planks |
| Python data/docs/preparation tests, canonical validation, reference freshness, and strict MkDocs build | Passed, 39 Python tests |
| Unity asset preparation and freshness | Passed locally |
| Unity 6000.6.6f1 import and Edit Mode tests | Passed, 2 tests; loaded Newtonsoft binary matches the pinned UPM package |
| Unity 6000.6.6f1 Play Mode scene test | Passed, 1 test; Bootstrap finishes with 0 logs / 3 planks and an unchanged rejected batch |
| Windows x64 Mono player build and execution | Passed; build and headless player exit code 0, with the expected smoke completion message |
| IL2CPP and other player platforms | Not run |
| GitHub Actions execution | Not run locally; workflow contains standalone/staging checks only |

Editor/player verification uses an isolated copy under `.cache/unity-verification` so the already-open working project is not interrupted. This copy is a local test artifact, not a second source location. Both Editor test runs used batch mode, and the Mono player ran with `-batchmode -nographics`; visual rendering was not assessed. NUnit XML results and Editor/build/player logs are retained locally under `.cache/` and are not version controlled.

For an intended IL2CPP target, install its Unity build support and native compiler prerequisites, select Bootstrap in the Build Profile, set **Scripting Backend: IL2CPP**, retain **API Compatibility Level: .NET Standard 2.1**, and select the intended managed stripping level. Build a development player, launch it with the smoke flag, and inspect its exit code and log as above. Record Editor version, operating system, target architecture, backend, stripping level, UPM version, and result. No blanket `link.xml` is supplied; investigate concrete stripping failures before adding preservation rules.

The smoke verifies assembly import, Unity's JSON dependency, packaged content loading, successful production, and an atomic rejection. It does not validate a production content-distribution system, save games, performance, every malformed input on every backend, or all player targets.

## Version control

Commit authored `Assets` and their `.meta` files, `Packages/manifest.json`, `Packages/packages-lock.json`, and `ProjectSettings`. Keep the root standalone solution and its project files. Ignore Unity's generated IDE projects/solution, `.vscode`, `Library`, `Temp`, `Logs`, `UserSettings`, build outputs, recordings, and the prepared `Assets/Generated` tree/manifest. The preparation command reconstructs the ignored integration assets on a fresh checkout.
